# API товаров

Базовый адрес локального приложения: `http://localhost:8080`.
Тело запроса и непустые ответы передаются в JSON.
В теле допускается ровно один JSON-объект с пробелами и переносами строк вокруг него.
Второе значение или мусор после объекта возвращают `400` с сообщением
`тело запроса должно содержать только один JSON-объект`.

В текущем `main.go` middleware `NoStore` не подключён,
поэтому заголовок `Cache-Control: no-store` автоматически не добавляется.

## Аутентификация

Все пять маршрутов API товаров требуют access-токен, полученный при
[входе пользователя](auth.md#вход-пользователя), включая список и получение по ID.
В каждом запросе передавай заголовок:

```http
Authorization: Bearer <access_token>
```

В примерах ниже замени `<access_token>` на значение поля `access_token`
из ответа входа. Refresh-токен для доступа к API не подходит.

Middleware `UserAuthenticator.Authenticate` проверяет заголовок и вызывает
`ValidateToken` в AUTH по gRPC. Обработчик товаров выполняется только после
успешной проверки; при отказе запрос не доходит до операций с товарами.

Общие ошибки аутентификации для всех маршрутов:

| Статус | Причина |
|---|---|
| `401 Unauthorized` | Заголовок отсутствует или имеет неверный формат; AUTH вернул `Unauthenticated`, `InvalidArgument` или `NotFound` |
| `500 Internal Server Error` | Остальные ошибки проверки в AUTH, включая недоступность сервиса |

Ответы возвращаются в JSON с полем `errors`. При `401` добавляется
заголовок `WWW-Authenticate: Bearer`.
Например, при отсутствии заголовка авторизации:

```json
{
  "errors": "некорректный заголовок авторизации"
}
```

Серверный `ValidateToken` преобразует любую ошибку поиска пользователя
в `NotFound`, поэтому сбой хранилища на этом этапе также приведёт к `401`.
Далее в разделах перечислены ошибки самих обработчиков после успешной аутентификации.

## Добавление товара

```http
POST /api/v1/products
Content-Type: application/json
```

Создаёт товар с переданными данными. UUID товара генерирует сервер,
дату последней закупки задаёт отправитель. Поставщик с указанным `supplier_id` должен
уже существовать в базе данных. Если передан `image_id`, изображение также
должно существовать. Этот запрос не создаёт поставщика или изображение.

### Поля запроса

Все поля, кроме `image_id`, обязательны.

| Поле | Описание | Формат |
|---|---|---|
| `name` | Название товара | Непустая строка |
| `category` | Категория товара | Непустая строка |
| `price` | Цена товара | Неотрицательное число |
| `available_stock` | Число закупленных экземпляров товара | Целое число от `0` до `2147483647` |
| `last_update_date` | Дата и время последней закупки | Строка RFC3339 с часовым поясом, например `2026-10-15T10:00:00Z` |
| `supplier_id` | Идентификатор существующего поставщика | Строка UUID |
| `image_id` | Идентификатор существующего изображения | Строка UUID или `null`; поле можно не передавать |

Название и категория не могут состоять только из пробелов.
Для категории сейчас не задан список допустимых значений.
Цена и количество могут быть нулевыми, но пропуск этих полей или `null`
недопустимы. Цена и количество передаются числами, без кавычек.
Пустая строка в `image_id` недопустима; отсутствие поля или `null` означает
товар без изображения.
Неизвестные поля игнорируются. Поле `id` не входит в запрос создания;
его передача не влияет на UUID, который сгенерирует сервер.

### Пример запроса

Перед отправкой замени `supplier_id` на идентификатор существующего поставщика.

```sh
curl -i -X POST http://localhost:8080/api/v1/products \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Чайник",
    "category": "Кухонная техника",
    "price": 2499.99,
    "available_stock": 10,
    "last_update_date": "2026-10-15T10:00:00Z",
    "supplier_id": "22222222-2222-4222-8222-222222222222",
    "image_id": null
  }'
```

Чтобы создать товар с изображением, передай в `image_id` UUID существующей
записи таблицы `images` вместо `null`.

### Успешный ответ

Статус: `201 Created`. Товар сохранён в базе данных.
Заголовок ответа: `Content-Type: application/json`.
Поле `id` содержит сгенерированный сервером UUID сохранённого товара.
Сохрани его для последующих запросов. UUID ниже приведён для примера.

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "name": "Чайник",
  "category": "Кухонная техника",
  "price": 2499.99,
  "available_stock": 10,
  "last_update_date": "2026-10-15T10:00:00Z",
  "supplier_id": "22222222-2222-4222-8222-222222222222",
  "image_id": null
}
```

Если изображение не указано, в ответе `image_id` всегда имеет значение `null`.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Неверный JSON, пропущенное обязательное поле, неверный тип значения, UUID или дата; отрицательная цена или количество вне допустимого диапазона |
| `500 Internal Server Error` | Ошибка сохранения в БД, включая отсутствующего поставщика или указанное отсутствующее изображение |

Например, если не передать цену, ответ будет иметь статус `400`:

```json
{
  "errors": "поле price обязательно"
}
```

При количестве `-1` ответ будет иметь статус `400`:

```json
{
  "errors": "поле available_stock должно быть целым числом от 0 до 2147483647"
}
```

Текст ошибки сохранения зависит от причины и сообщения PostgreSQL.

## Уменьшение количества товара

```http
PATCH /api/v1/products/{id}/stock
Content-Type: application/json
```

Уменьшает `available_stock` товара на переданное количество. В пути передаётся
UUID товара, а в JSON — число экземпляров, которое нужно списать.
Остальные поля товара не меняются. В частности, `last_update_date` остаётся
прежней: это дата последней закупки, а не списания.

### Поля запроса

| Поле | Описание | Формат |
|---|---|---|
| `quantity` | На сколько уменьшить количество товара | Обязательное целое число от `1` до `2147483647` |

Количество передаётся числом, без кавычек. Пропуск поля, `null`, ноль,
отрицательное или дробное значение недопустимы.
Можно списать весь остаток до нуля. Если количества недостаточно, списание
не выполняется, остаток сохраняется.

### Пример запроса

Замени идентификатор в пути на UUID существующего товара с остатком не менее `3`.

```sh
curl -i -X PATCH \
  http://localhost:8080/api/v1/products/11111111-1111-4111-8111-111111111111/stock \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{"quantity": 3}'
```

### Успешный ответ

Статус: `204 No Content`. Тело ответа отсутствует.
Например, при исходном остатке `10` после запроса из примера в БД останется `7`.

Репозиторий сначала проверяет наличие товара. Проверка достаточного остатка
и его уменьшение выполняются одним условным `UPDATE`. Это предотвращает
списание сверх остатка при одновременных запросах. Например, при остатке `5`
из двух одновременных запросов на списание по `3` успешно выполнится только один;
второй получит `409`, а остаток станет `2`.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный UUID товара, JSON или `quantity` |
| `404 Not Found` | Товар отсутствует |
| `409 Conflict` | Остатка товара недостаточно для списания |
| `500 Internal Server Error` | Ошибка проверки наличия товара или уменьшения количества в БД |

При отсутствии товара ответ будет иметь статус `404`:

```json
{
  "errors": "товар не найден"
}
```

При недостаточном остатке ответ будет иметь статус `409`:

```json
{
  "errors": "недостаточный остаток товара"
}
```

При `quantity: 0` ответ будет иметь статус `400`:

```json
{
  "errors": "поле quantity должно быть целым числом от 1 до 2147483647"
}
```

При ошибке БД текст сообщения зависит от причины ошибки.

## Получение товара по ID

```http
GET /api/v1/products/{id}
```

Возвращает товар по UUID из пути запроса независимо от остатка, включая нулевой.
Тело запроса не требуется.

### Пример запроса

Замени идентификатор в пути на UUID существующего товара.

```sh
curl -i \
  http://localhost:8080/api/v1/products/11111111-1111-4111-8111-111111111111 \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `200 OK`. Заголовок ответа: `Content-Type: application/json`.
Возвращаются те же поля, что и при добавлении товара.

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "name": "Чайник",
  "category": "Кухонная техника",
  "price": 2499.99,
  "available_stock": 10,
  "last_update_date": "2026-10-15T10:00:00Z",
  "supplier_id": "22222222-2222-4222-8222-222222222222",
  "image_id": null
}
```

У товара без изображения `image_id` имеет значение `null`.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Идентификатор в пути не является корректным UUID |
| `404 Not Found` | Товар с указанным UUID отсутствует, в том числе после удаления |
| `500 Internal Server Error` | Ошибка получения или чтения товара из БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При отсутствии товара ответ будет иметь статус `404`:

```json
{
  "errors": "товар не найден"
}
```

При ошибке БД текст сообщения зависит от причины ошибки.

## Получение всех доступных товаров

```http
GET /api/v1/products
GET /api/v1/products?limit=10&offset=20
```

Возвращает только товары с `available_stock > 0`, отсортированные по `id`
по возрастанию. Тело запроса не требуется.
Без параметров возвращает весь список доступных товаров.

Пагинация добавлена по согласованию сверх требований README по аналогии с API
клиентов. Отбор доступных товаров выполняется до применения `limit` и `offset`.

### Параметры пагинации

Оба параметра необязательны и передаются в строке запроса.
Каждый из них можно использовать отдельно.

| Параметр | Описание | Если отсутствует |
|---|---|---|
| `limit` | Максимальное количество возвращаемых товаров; `0` возвращает `[]` | Без ограничения количества |
| `offset` | Количество доступных товаров, которые нужно пропустить | `0` |

Значения должны быть целыми числами от `0` до `9223372036854775807`.
Пустые значения, пробелы, дробные и отрицательные числа недопустимы.
Если `offset` не меньше количества доступных товаров, возвращается `[]`.

### Примеры запросов

Все доступные товары:

```sh
curl -i http://localhost:8080/api/v1/products \
  -H 'Authorization: Bearer <access_token>'
```

Пропустить первые 20 доступных товаров и вернуть следующие 10 или меньше:

```sh
curl -i 'http://localhost:8080/api/v1/products?limit=10&offset=20' \
  -H 'Authorization: Bearer <access_token>'
```

Только первые 10 доступных товаров:

```sh
curl -i 'http://localhost:8080/api/v1/products?limit=10' \
  -H 'Authorization: Bearer <access_token>'
```

Все доступные товары после первых 10:

```sh
curl -i 'http://localhost:8080/api/v1/products?offset=10' \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `200 OK`. Заголовок ответа: `Content-Type: application/json`.
Тело ответа — массив товаров с теми же полями, что и при получении по ID.

```json
[
  {
    "id": "11111111-1111-4111-8111-111111111111",
    "name": "Чайник",
    "category": "Кухонная техника",
    "price": 2499.99,
    "available_stock": 10,
    "last_update_date": "2026-10-15T10:00:00Z",
    "supplier_id": "22222222-2222-4222-8222-222222222222",
    "image_id": null
  }
]
```

Если доступных товаров нет или страница пуста, возвращается `[]`.
После списания всего остатка товар исчезает из списка, но остаётся доступен по ID.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный `limit` или `offset` |
| `500 Internal Server Error` | Ошибка получения или чтения списка товаров из БД |

Например, при `limit=-1` ответ будет иметь статус `400`:

```json
{
  "errors": "параметр limit должен быть целым неотрицательным числом. Пример запроса: /api/v1/products?limit=10&offset=20"
}
```

При ошибке БД текст сообщения зависит от причины ошибки.

## Удаление товара

```http
DELETE /api/v1/products/{id}
```

Удаляет товар по UUID из пути запроса. Тело запроса не требуется.
Поставщик и изображение остаются в базе данных. Другие товары не изменяются,
в том числе товары с тем же поставщиком или изображением.
Удаление допускается при любом остатке, включая нулевой.

### Пример запроса

Замени идентификатор в пути на UUID существующего товара.

```sh
curl -i -X DELETE \
  http://localhost:8080/api/v1/products/11111111-1111-4111-8111-111111111111 \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `204 No Content`. Товар удалён из базы данных.
Тело ответа отсутствует.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Идентификатор в пути не является корректным UUID |
| `404 Not Found` | Товар с указанным UUID отсутствует, в том числе при повторном удалении |
| `500 Internal Server Error` | Ошибка удаления в БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При отсутствии товара ответ будет иметь статус `404`:

```json
{
  "errors": "товар не найден"
}
```

При ошибке БД сообщение начинается с `ошибка при удалении товара:`.
Остальная часть сообщения зависит от причины ошибки PostgreSQL.
