# API изображений

Базовый адрес локального приложения: `http://localhost:8080`.
Тело запросов добавления и изменения содержит исходные байты файла.
Получение изображения возвращает исходные байты файла. Ответ добавления и ошибки
передаются в JSON; успешные изменение и удаление возвращают ответ без тела.

В текущем `main.go` middleware `NoStore` не подключён,
поэтому заголовок `Cache-Control: no-store` автоматически не добавляется.

## Аутентификация

Все пять маршрутов API изображений требуют access-токен, полученный при
[входе пользователя](auth.md#вход-пользователя), включая оба метода скачивания.
В каждом запросе передавай заголовок:

```http
Authorization: Bearer <access_token>
```

В примерах ниже замени `<access_token>` на значение поля `access_token`
из ответа входа. Refresh-токен для доступа к API не подходит.

Middleware `UserAuthenticator.Authenticate` проверяет заголовок и вызывает
`ValidateToken` в AUTH по gRPC. Обработчик изображений выполняется только после
успешной проверки; при отказе запрос не доходит до операций с изображениями.

Общие ошибки аутентификации для всех маршрутов:

| Статус | Причина |
|---|---|
| `401 Unauthorized` | Заголовок отсутствует или имеет неверный формат; AUTH вернул `Unauthenticated`, `InvalidArgument` или `NotFound` |
| `500 Internal Server Error` | Остальные ошибки проверки в AUTH, включая недоступность сервиса |

Ответы возвращаются в JSON с полем `errors`, в том числе при запросе скачивания.
При `401` добавляется заголовок `WWW-Authenticate: Bearer`.
Заголовок `Content-Disposition` при отказе аутентификации отсутствует.
Например, при отсутствии заголовка авторизации:

```json
{
  "errors": "некорректный заголовок авторизации"
}
```

Серверный `ValidateToken` преобразует любую ошибку поиска пользователя
в `NotFound`, поэтому сбой хранилища на этом этапе также приведёт к `401`.
Далее в разделах перечислены ошибки самих обработчиков после успешной аутентификации.

## Добавление изображения

```http
POST /api/v1/products/{id}/image
Content-Type: application/octet-stream
```

Создаёт изображение и связывает его с существующим товаром по UUID из пути.
UUID нового изображения генерирует сервер. У товара не должно быть изображения:
существующая связь не заменяется, прежнее изображение не удаляется.

Сохранение изображения и привязка к товару выполняются в одной транзакции.
Если товара нет или связь уже занята, вставка изображения отменяется.
Другие поля товара, изображения и ссылки других товаров сохраняются.

### Данные запроса

| Данные | Описание | Формат |
|---|---|---|
| `id` в пути | Идентификатор существующего товара | UUID |
| Тело | Исходные байты изображения | Непустой массив байт |

JSON, base64 и multipart не используются. Расширение, MIME-тип и содержимое
файла не проверяются. Тело целиком читается в память; ограничение размера
на уровне приложения не установлено.

### Пример запроса

Замени идентификатор в пути на UUID существующего товара без изображения,
а `./image.png` — на путь к непустому файлу.
Параметр `--data-binary` передаёт байты файла без преобразований.

```sh
curl -i -X POST \
  http://localhost:8080/api/v1/products/11111111-1111-4111-8111-111111111111/image \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/octet-stream' \
  --data-binary @./image.png
```

### Успешный ответ

Статус: `201 Created`. Изображение сохранено, его UUID записан в `product.image_id`.
Заголовок ответа: `Content-Type: application/json`.

```json
{
  "id": "22222222-2222-4222-8222-222222222222"
}
```

Значение `id` в примере условное: каждый успешный запрос создаёт новый UUID.
Байты изображения в ответ не включаются.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный UUID товара, пустое тело или ошибка чтения тела |
| `404 Not Found` | Товар с указанным UUID отсутствует |
| `409 Conflict` | У товара уже есть изображение |
| `500 Internal Server Error` | Ошибка работы с БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При пустом теле сообщение — `данные изображения не должны быть пустыми`,
при ошибке чтения — `ошибка чтения данных изображения`.

При отсутствии товара ответ будет иметь статус `404`:

```json
{
  "errors": "товар не найден"
}
```

При занятой связи, в том числе при повторном добавлении, ответ будет иметь статус `409`:

```json
{
  "errors": "у товара уже есть изображение"
}
```

В случаях `404` и `409` новая запись изображения не остаётся в БД.

## Изменение изображения

```http
PUT /api/v1/images/{id}
Content-Type: application/octet-stream
```

Полностью заменяет содержимое существующего изображения по UUID из пути.
Формулировка README «новая строка для замены» трактуется как новые байты файла.
UUID изображения сохраняется, новая запись не создаётся.

Несколько товаров могут ссылаться на одно изображение. Замена меняет общее
содержимое для всех таких товаров; значения `product.image_id` и остальные
поля товаров сохраняются. Изображение можно изменить и без привязки к товару.

### Данные запроса

| Данные | Описание | Формат |
|---|---|---|
| `id` в пути | Идентификатор существующего изображения | UUID |
| Тело | Новое содержимое изображения | Непустой массив байт |

Передаются исходные байты без JSON, base64 и multipart. Расширение, MIME-тип
и содержимое файла не проверяются. Тело целиком читается в память;
ограничение размера на уровне приложения не установлено.

### Пример запроса

Замени идентификатор в пути на UUID изображения, например из ответа добавления,
а `./replacement.png` — на путь к новому непустому файлу.

```sh
curl -i -X PUT \
  http://localhost:8080/api/v1/images/22222222-2222-4222-8222-222222222222 \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/octet-stream' \
  --data-binary @./replacement.png
```

### Успешный ответ

Статус: `204 No Content`. Байты изображения заменены.
Тело ответа отсутствует, JSON не кодируется.
Повторная передача тех же байтов также возвращает `204`.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный UUID изображения, пустое тело или ошибка чтения тела |
| `404 Not Found` | Изображение с указанным UUID отсутствует |
| `500 Internal Server Error` | Ошибка изменения в БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При пустом теле сообщение — `данные изображения не должны быть пустыми`,
при ошибке чтения — `ошибка чтения данных изображения`.
В этих случаях прежние байты сохраняются.

При отсутствии изображения ответ будет иметь статус `404`:

```json
{
  "errors": "изображение не найдено"
}
```

При ошибке БД сообщение начинается с `ошибка при изменении изображения:`.
Остальная часть сообщения зависит от причины ошибки PostgreSQL.

## Удаление изображения

```http
DELETE /api/v1/images/{id}
```

Удаляет изображение по UUID из пути запроса. Тело запроса не требуется.
Можно удалить изображение как со связанными товарами, так и без них.

Внешний ключ `product.image_id` содержит правило `ON DELETE SET NULL`:
PostgreSQL автоматически обнуляет ссылки всех товаров на удалённое изображение.
Сами товары и остальные их поля сохраняются; получение этих товаров через API
возвращает `image_id: null`. Другие изображения и ссылки на них не изменяются.
Удаление и обнуление ссылок выполняются атомарно одним SQL-запросом.

### Пример запроса

Замени идентификатор в пути на UUID существующего изображения.

```sh
curl -i -X DELETE \
  http://localhost:8080/api/v1/images/22222222-2222-4222-8222-222222222222 \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `204 No Content`. Изображение удалено из базы данных.
Тело ответа отсутствует, JSON не кодируется.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Идентификатор в пути не является корректным UUID |
| `404 Not Found` | Изображение отсутствует, в том числе при повторном удалении |
| `500 Internal Server Error` | Ошибка удаления в БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При отсутствии изображения ответ будет иметь статус `404`:

```json
{
  "errors": "изображение не найдено"
}
```

При ошибке БД сообщение начинается с `ошибка при удалении изображения:`.
Остальная часть сообщения зависит от причины ошибки PostgreSQL.

## Получение изображения по ID

```http
GET /api/v1/images/{id}
```

Возвращает файл изображения по UUID из пути запроса. Тело запроса не требуется.
Изображение доступно независимо от наличия связанных товаров.
Запрос не изменяет данные в БД.

### Пример запроса

Замени идентификатор в пути на UUID существующего изображения.
Параметр `-o` сохраняет байты в файл `./downloaded.bin`, а `-D -` выводит
заголовки отдельно от содержимого файла. `--fail` завершает команду с ошибкой
при HTTP-статусе `400` или выше и не сохраняет JSON ошибки как изображение.

```sh
curl --fail -D - \
  http://localhost:8080/api/v1/images/22222222-2222-4222-8222-222222222222 \
  -H 'Authorization: Bearer <access_token>' \
  -o ./downloaded.bin
```

Чтобы использовать имя файла из заголовка ответа, выполни запрос с `-OJ`
в каталоге, куда нужно скачать файл:

```sh
curl --fail -D - -OJ \
  http://localhost:8080/api/v1/images/22222222-2222-4222-8222-222222222222 \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `200 OK`. Тело содержит исходные байты изображения без JSON и base64.

```http
Content-Type: application/octet-stream
Content-Disposition: attachment; filename="22222222-2222-4222-8222-222222222222.bin"
```

`attachment` предлагает клиенту скачать файл. Имя формируется из UUID изображения
в БД с расширением `.bin`: исходное имя файла и его MIME-тип не хранятся.
После изменения изображения запрос возвращает новые байты под тем же именем,
после удаления — `404 Not Found`.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Заголовок `Content-Disposition` отсутствует. Поле `errors` содержит сообщение.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Идентификатор в пути не является корректным UUID |
| `404 Not Found` | Изображение с указанным UUID отсутствует |
| `500 Internal Server Error` | Ошибка получения из БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При отсутствии изображения ответ будет иметь статус `404`:

```json
{
  "errors": "изображение не найдено"
}
```

При ошибке БД сообщение начинается с `ошибка при получении изображения:`.
Остальная часть сообщения зависит от причины ошибки PostgreSQL.

## Получение изображения по ID товара

```http
GET /api/v1/products/{id}/image
```

Возвращает файл изображения, на которое ссылается товар с UUID из пути запроса.
Тело запроса не требуется. Поиск выполняется через связь `product.image_id`.
Запрос не изменяет данные в БД.

### Пример запроса

Замени идентификатор в пути на UUID существующего товара с изображением.
Параметр `-o` сохраняет байты в файл, а `-D -` выводит заголовки отдельно.
`--fail` предотвращает сохранение JSON ошибки как изображения при HTTP-статусе
`400` или выше.

```sh
curl --fail -D - \
  http://localhost:8080/api/v1/products/11111111-1111-4111-8111-111111111111/image \
  -H 'Authorization: Bearer <access_token>' \
  -o ./product-image.bin
```

Для сохранения под именем из заголовка ответа используй `-OJ`:

```sh
curl --fail -D - -OJ \
  http://localhost:8080/api/v1/products/11111111-1111-4111-8111-111111111111/image \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `200 OK`. Тело содержит исходные байты изображения без JSON и base64.

```http
Content-Type: application/octet-stream
Content-Disposition: attachment; filename="22222222-2222-4222-8222-222222222222.bin"
```

Имя файла содержит UUID изображения, а не товара. Оба метода получения используют
одинаковую отправку файла. Если несколько товаров ссылаются на одно изображение,
они возвращают одинаковые байты и имя файла. После замены изображения
все связанные товары возвращают новые байты.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Заголовок `Content-Disposition` отсутствует. Поле `errors` содержит сообщение.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Идентификатор товара в пути не является корректным UUID |
| `404 Not Found` | Товар отсутствует или у существующего товара нет изображения |
| `500 Internal Server Error` | Ошибка получения изображения или проверки наличия товара в БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При отсутствии товара ответ будет иметь статус `404`:

```json
{
  "errors": "товар не найден"
}
```

Если товар существует, но его `image_id` равен `NULL`, ответ также имеет статус
`404`, с другим сообщением:

```json
{
  "errors": "у товара нет изображения"
}
```

Такой ответ возвращается и после удаления связанного изображения:
`ON DELETE SET NULL` сохраняет товар и обнуляет его ссылку.

При ошибке БД сообщение начинается с `ошибка при получении изображения товара:`
или `ошибка при проверке наличия товара:`. Остальная часть зависит от причины
ошибки PostgreSQL.
