# API клиентов

Базовый адрес локального приложения: `http://localhost:8080`.
Тело запроса и непустые ответы передаются в JSON.
В теле допускается ровно один JSON-объект с пробелами и переносами строк вокруг него.
Второе значение или мусор после объекта возвращают `400` с сообщением
`тело запроса должно содержать только один JSON-объект`.

В текущем `main.go` middleware `NoStore` не подключён,
поэтому заголовок `Cache-Control: no-store` автоматически не добавляется.

## Аутентификация

Все четыре маршрута API клиентов требуют access-токен, полученный при
[входе пользователя](auth.md#вход-пользователя), включая поиск и список клиентов.
В каждом запросе передавай заголовок:

```http
Authorization: Bearer <access_token>
```

В примерах ниже замени `<access_token>` на значение поля `access_token`
из ответа входа. Refresh-токен для доступа к API не подходит.

Middleware `UserAuthenticator.Authenticate` проверяет заголовок и вызывает
`ValidateToken` в AUTH по gRPC. Обработчик клиентов выполняется только после
успешной проверки; при отказе запрос не доходит до операций с клиентами.

Общие ошибки аутентификации для всех маршрутов:

| Статус | Причина |
|---|---|
| `401 Unauthorized` | Заголовок отсутствует или имеет неверный формат; AUTH вернул `Unauthenticated`, `InvalidArgument` или `NotFound` |
| `500 Internal Server Error` | Остальные ошибки проверки в AUTH, включая недоступность сервиса |

Ответы возвращаются в JSON с полем `errors`. При `401` добавляется
заголовок `WWW-Authenticate: Bearer`.
Например, при отсутствии заголовка авторизации:

```json
{
  "errors": "некорректный заголовок авторизации"
}
```

Серверный `ValidateToken` преобразует любую ошибку поиска пользователя
в `NotFound`, поэтому сбой хранилища на этом этапе также приведёт к `401`.
Далее в разделах перечислены ошибки самих обработчиков после успешной аутентификации.

## Добавление клиента

```http
POST /api/v1/clients
Content-Type: application/json
```

Создаёт клиента с переданными данными. UUID клиента генерирует сервер,
дату регистрации задаёт отправитель. Адрес с указанным `address_id` должен уже существовать
в базе данных; этот запрос не создаёт адрес.

### Поля запроса

Все поля обязательны и передаются строками.

| Поле | Описание | Формат |
|---|---|---|
| `client_name` | Имя клиента | Непустая строка |
| `client_surname` | Фамилия клиента | Непустая строка |
| `birthday` | Дата рождения | Корректная дата `YYYY-MM-DD` |
| `gender` | Пол клиента | Непустая строка, например `male` |
| `registration_date` | Дата и время регистрации | RFC3339 с часовым поясом, например `2026-10-14T12:00:00Z` или `2026-10-14T15:00:00+03:00` |
| `address_id` | Идентификатор существующего адреса | UUID |

Имя, фамилия и пол не могут состоять только из пробелов.
Для `gender` сейчас не задан список допустимых значений.
Неизвестные поля игнорируются. Поле `id` не входит в запрос создания;
его передача не влияет на UUID, который сгенерирует сервер.

### Пример запроса

Перед отправкой замени `address_id` на идентификатор существующего адреса.

```sh
curl -i -X POST http://localhost:8080/api/v1/clients \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{
    "client_name": "Иван",
    "client_surname": "Иванов",
    "birthday": "1995-05-20",
    "gender": "male",
    "registration_date": "2026-10-14T12:00:00Z",
    "address_id": "22222222-2222-4222-8222-222222222222"
  }'
```

### Успешный ответ

Статус: `201 Created`. Клиент сохранён в базе данных.
Заголовок ответа: `Content-Type: application/json`.
Поле `id` содержит сгенерированный сервером UUID сохранённого клиента.
Сохрани его для последующих запросов. UUID ниже приведён для примера.

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "client_name": "Иван",
  "client_surname": "Иванов",
  "birthday": "1995-05-20",
  "gender": "male",
  "registration_date": "2026-10-14T12:00:00Z",
  "address_id": "22222222-2222-4222-8222-222222222222"
}
```

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Неверный JSON, пропущенное обязательное поле, неверный тип значения, UUID или дата |
| `500 Internal Server Error` | Ошибка сохранения в БД, включая отсутствующий адрес |

Например, если передать пустое имя, ответ будет иметь статус `400`:

```json
{
  "errors": "поле client_name обязательно"
}
```

При некорректном `address_id` сообщение — `поле address_id должно содержать корректный UUID`.
При ошибке БД сообщение начинается с `ошибка при сохранении клиента:`.
Остальная часть сообщения зависит от причины и сообщения PostgreSQL.

## Удаление клиента

```http
DELETE /api/v1/clients/{id}
```

Удаляет клиента по UUID из пути запроса. Тело запроса не требуется.
Связанный адрес остаётся в базе данных.

### Пример запроса

Замени идентификатор в пути на UUID существующего клиента.

```sh
curl -i -X DELETE \
  http://localhost:8080/api/v1/clients/11111111-1111-4111-8111-111111111111 \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `204 No Content`. Клиент удалён из базы данных.
Тело ответа отсутствует.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Идентификатор в пути не является корректным UUID |
| `404 Not Found` | Клиент с указанным UUID отсутствует, в том числе при повторном удалении |
| `500 Internal Server Error` | Ошибка удаления в БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При отсутствии клиента ответ будет иметь статус `404`:

```json
{
  "errors": "клиент не найден"
}
```

При ошибке БД сообщение начинается с `ошибка при удалении клиента:`.
Остальная часть сообщения зависит от причины ошибки PostgreSQL.

## Получение клиентов по имени и фамилии

```http
GET /api/v1/clients?client_name=Иван&client_surname=Иванов
```

Возвращает всех клиентов с точным совпадением имени и фамилии одновременно.
Поиск учитывает регистр. Тело запроса не требуется.

### Параметры запроса

Для поиска оба параметра обязательны и передаются в строке запроса.
Если оба отсутствуют, запрос возвращает список всех клиентов, описанный ниже.
Параметры поиска нельзя совмещать с `limit` или `offset`.

| Параметр | Описание |
|---|---|
| `client_name` | Имя клиента |
| `client_surname` | Фамилия клиента |

Значения не могут быть пустыми или состоять только из пробелов.
Пробелы по краям непустых значений не удаляются и участвуют в поиске.

### Пример запроса

`--data-urlencode` кодирует значения параметров для передачи в URL.
Флаг `--get` добавляет их в строку запроса.

```sh
curl -i --get http://localhost:8080/api/v1/clients \
  -H 'Authorization: Bearer <access_token>' \
  --data-urlencode 'client_name=Иван' \
  --data-urlencode 'client_surname=Иванов'
```

### Успешный ответ

Статус: `200 OK`. Заголовок ответа: `Content-Type: application/json`.
Тело ответа — массив клиентов с теми же полями, что и в ответе добавления клиента.
Порядок элементов не гарантируется.

```json
[
  {
    "id": "11111111-1111-4111-8111-111111111111",
    "client_name": "Иван",
    "client_surname": "Иванов",
    "birthday": "1995-05-20",
    "gender": "male",
    "registration_date": "2026-10-14T12:00:00Z",
    "address_id": "22222222-2222-4222-8222-222222222222"
  }
]
```

Если совпадений нет, возвращается `200 OK` с пустым массивом `[]`.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | При поиске имя или фамилия отсутствует, имеет пустое значение или состоит только из пробелов; поиск совмещён с пагинацией |
| `500 Internal Server Error` | Ошибка поиска или чтения данных из БД |

Например, при отсутствии фамилии ответ будет иметь статус `400`:

```json
{
  "errors": "поле client_surname обязательно. Пример запроса: /api/v1/clients?client_name=Иван&client_surname=Иванов"
}
```

## Получение всех клиентов

```http
GET /api/v1/clients
GET /api/v1/clients?limit=10&offset=20
```

Без параметров возвращает всех клиентов. Тело запроса не требуется.
Клиенты отсортированы по `id` по возрастанию.

### Параметры пагинации

Оба параметра необязательны и передаются в строке запроса.
Каждый из них можно использовать отдельно.

| Параметр | Описание | Если отсутствует |
|---|---|---|
| `limit` | Максимальное количество возвращаемых клиентов; `0` возвращает `[]` | Без ограничения количества |
| `offset` | Количество клиентов, которые нужно пропустить | `0` |

Значения должны быть целыми числами от `0` до `9223372036854775807`.
Пустые значения, пробелы, дробные и отрицательные числа недопустимы.
Если `offset` не меньше количества клиентов, возвращается `[]`.

### Примеры запросов

Все клиенты:

```sh
curl -i http://localhost:8080/api/v1/clients \
  -H 'Authorization: Bearer <access_token>'
```

Пропустить первые 20 клиентов и вернуть следующие 10 или меньше:

```sh
curl -i 'http://localhost:8080/api/v1/clients?limit=10&offset=20' \
  -H 'Authorization: Bearer <access_token>'
```

Только первые 10 клиентов:

```sh
curl -i 'http://localhost:8080/api/v1/clients?limit=10' \
  -H 'Authorization: Bearer <access_token>'
```

Все клиенты после первых 10:

```sh
curl -i 'http://localhost:8080/api/v1/clients?offset=10' \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `200 OK`. Заголовок ответа: `Content-Type: application/json`.
Тело ответа — массив клиентов с теми же полями, что и в ответе поиска по имени
и фамилии. Если клиентов нет или страница пуста, возвращается `[]`.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный `limit` или `offset`; пагинация совмещена с параметрами поиска |
| `500 Internal Server Error` | Ошибка получения или чтения списка из БД |

Например, при `limit=-1` ответ будет иметь статус `400`:

```json
{
  "errors": "параметр limit должен быть целым неотрицательным числом. Пример запроса: /api/v1/clients?limit=10&offset=20"
}
```

## Изменение адреса клиента

```http
PUT /api/v1/clients/{id}/address
Content-Type: application/json
```

В пути передаётся UUID клиента, а в JSON — страна, город и улица нового адреса.
Если страна, город или улица отличаются от текущих, сервер создаёт новый адрес,
генерирует его UUID и меняет `address_id` только указанного клиента.
UUID клиента сохраняется.
Старый адрес сохраняется. Адреса остальных клиентов и поставщиков не изменяются.

### Поля запроса

Все поля обязательны и передаются строками.

| Поле | Описание | Формат |
|---|---|---|
| `country` | Страна | Непустая строка |
| `city` | Город | Непустая строка |
| `street` | Улица | Непустая строка |

Страна, город и улица не могут состоять только из пробелов.
Неизвестные поля игнорируются, в том числе переданный `id`.

### Пример запроса

Замени UUID клиента в пути на существующий.

```sh
curl -i -X PUT \
  http://localhost:8080/api/v1/clients/11111111-1111-4111-8111-111111111111/address \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{
    "country": "Россия",
    "city": "Казань",
    "street": "Ленина"
  }'
```

### Успешный ответ

Статус: `200 OK`. Заголовок ответа: `Content-Type: application/json`.
В JSON возвращается установленный адрес. Поле `id` содержит его UUID;
в ответах поиска и получения списка у клиента будет такой же `address_id`.
UUID ниже приведён для примера.

```json
{
  "id": "33333333-3333-4333-8333-333333333333",
  "country": "Россия",
  "city": "Казань",
  "street": "Ленина"
}
```

Если все три поля совпадают с текущим адресом, возвращается этот адрес с прежним
UUID без создания записи и изменения `address_id`. Сравнение точное, с учётом
регистра и пробелов. Последовательный повтор одинакового PUT сохраняет UUID.

Перед вставкой читается текущий адрес клиента. Если клиента нет, возвращается
`404` без вставки адреса. Чтение текущего адреса, создание нового адреса и изменение
ссылки выполняются в одной транзакции. При ошибке изменения отменяются.
Дополнительные блокировки для защиты от параллельных PUT не предусмотрены.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный UUID клиента, JSON или обязательные поля адреса |
| `404 Not Found` | Клиент отсутствует; новый адрес не создаётся |
| `500 Internal Server Error` | Ошибка БД |

При отсутствии клиента ответ будет иметь статус `404`:

```json
{
  "errors": "клиент не найден"
}
```

При некорректном UUID клиента в пути ответ будет иметь статус `400`:

```json
{
  "errors": "идентификатор клиента должен содержать корректный UUID"
}
```

При ошибке БД текст сообщения зависит от причины ошибки.
