# API поставщиков

Базовый адрес локального приложения: `http://localhost:8080`.
Тело запроса и непустые ответы передаются в JSON.
В теле допускается ровно один JSON-объект с пробелами и переносами строк вокруг него.
Второе значение или мусор после объекта возвращают `400` с сообщением
`тело запроса должно содержать только один JSON-объект`.

В текущем `main.go` middleware `NoStore` не подключён,
поэтому заголовок `Cache-Control: no-store` автоматически не добавляется.

## Аутентификация

Все пять маршрутов API поставщиков требуют access-токен, полученный при
[входе пользователя](auth.md#вход-пользователя), включая список и получение по ID.
В каждом запросе передавай заголовок:

```http
Authorization: Bearer <access_token>
```

В примерах ниже замени `<access_token>` на значение поля `access_token`
из ответа входа. Refresh-токен для доступа к API не подходит.

Middleware `UserAuthenticator.Authenticate` проверяет заголовок и вызывает
`ValidateToken` в AUTH по gRPC. Обработчик поставщиков выполняется только после
успешной проверки; при отказе запрос не доходит до операций с поставщиками.

Общие ошибки аутентификации для всех маршрутов:

| Статус | Причина |
|---|---|
| `401 Unauthorized` | Заголовок отсутствует или имеет неверный формат; AUTH вернул `Unauthenticated`, `InvalidArgument` или `NotFound` |
| `500 Internal Server Error` | Остальные ошибки проверки в AUTH, включая недоступность сервиса |

Ответы возвращаются в JSON с полем `errors`. При `401` добавляется
заголовок `WWW-Authenticate: Bearer`.
Например, при отсутствии заголовка авторизации:

```json
{
  "errors": "некорректный заголовок авторизации"
}
```

Серверный `ValidateToken` преобразует любую ошибку поиска пользователя
в `NotFound`, поэтому сбой хранилища на этом этапе также приведёт к `401`.
Далее в разделах перечислены ошибки самих обработчиков после успешной аутентификации.

## Добавление поставщика

```http
POST /api/v1/suppliers
Content-Type: application/json
```

Создаёт поставщика с переданными данными. UUID поставщика генерирует
сервер. Адрес с указанным `address_id` должен уже существовать
в базе данных; этот запрос не создаёт адрес.

### Поля запроса

Все поля обязательны и передаются строками.

| Поле | Описание | Формат |
|---|---|---|
| `name` | Название поставщика | Непустая строка |
| `address_id` | Идентификатор существующего адреса | UUID |
| `phone_number` | Телефон поставщика | Непустая строка |

Название и телефон не могут состоять только из пробелов.
Формат телефона не ограничен. Пробелы по краям непустых значений сохраняются.
Неизвестные поля игнорируются. Поле `id` не входит в запрос создания;
его передача не влияет на UUID, который сгенерирует сервер.

### Пример запроса

Перед отправкой замени `address_id` на идентификатор существующего адреса.

```sh
curl -i -X POST http://localhost:8080/api/v1/suppliers \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Бытовая техника",
    "address_id": "22222222-2222-4222-8222-222222222222",
    "phone_number": "+7 (900) 123-45-67"
  }'
```

### Успешный ответ

Статус: `201 Created`. Поставщик сохранён в базе данных.
Заголовок ответа: `Content-Type: application/json`.
Поле `id` содержит сгенерированный сервером UUID сохранённого поставщика.
Сохрани его для последующих запросов и передачи в `supplier_id`.
UUID ниже приведён для примера.

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "name": "Бытовая техника",
  "address_id": "22222222-2222-4222-8222-222222222222",
  "phone_number": "+7 (900) 123-45-67"
}
```

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Неверный JSON, пропущенное обязательное поле, неверный тип значения, пустое название или телефон, некорректный UUID |
| `500 Internal Server Error` | Ошибка сохранения в БД, включая отсутствующий адрес |

Например, если передать пустой телефон, ответ будет иметь статус `400`:

```json
{
  "errors": "поле phone_number обязательно"
}
```

При некорректном UUID адреса ответ будет иметь статус `400`:

```json
{
  "errors": "поле address_id должно содержать корректный UUID"
}
```

При ошибке БД сообщение начинается с `ошибка при сохранении поставщика:`.
Остальная часть сообщения зависит от причины ошибки PostgreSQL.

## Удаление поставщика

```http
DELETE /api/v1/suppliers/{id}
```

Удаляет поставщика по UUID из пути запроса. Тело запроса не требуется.
Связанный адрес остаётся в базе данных. Другие поставщики и их товары не изменяются.

Если на поставщика ссылается хотя бы один товар, внешний ключ
`product.supplier_id` с `ON DELETE RESTRICT` запрещает удаление.
В этом случае возвращается `500 Internal Server Error`, поставщик и его товары
сохраняются. Нулевой остаток товара также препятствует удалению поставщика.

### Пример запроса

Замени идентификатор в пути на UUID существующего поставщика без товаров.

```sh
curl -i -X DELETE \
  http://localhost:8080/api/v1/suppliers/11111111-1111-4111-8111-111111111111 \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `204 No Content`. Поставщик удалён из базы данных.
Тело ответа отсутствует.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Идентификатор в пути не является корректным UUID |
| `404 Not Found` | Поставщик с указанным UUID отсутствует, в том числе при повторном удалении |
| `500 Internal Server Error` | Ошибка удаления в БД, включая наличие товаров у поставщика |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При отсутствии поставщика ответ будет иметь статус `404`:

```json
{
  "errors": "поставщик не найден"
}
```

При ошибке БД сообщение начинается с `ошибка при удалении поставщика:`.
Остальная часть сообщения зависит от причины ошибки PostgreSQL.

## Изменение адреса поставщика

```http
PUT /api/v1/suppliers/{id}/address
Content-Type: application/json
```

В пути передаётся UUID поставщика, а в JSON — страна, город и улица нового адреса.
Если страна, город или улица отличаются от текущих, сервер создаёт новый адрес,
генерирует его UUID и меняет `address_id` только указанного поставщика.
UUID поставщика сохраняется.
Старый адрес сохраняется. Адреса остальных поставщиков и клиентов, а также
товары поставщика не изменяются.

### Поля запроса

Все поля обязательны и передаются строками.

| Поле | Описание | Формат |
|---|---|---|
| `country` | Страна | Непустая строка |
| `city` | Город | Непустая строка |
| `street` | Улица | Непустая строка |

Страна, город и улица не могут состоять только из пробелов.
Пробелы по краям непустых значений сохраняются.
Неизвестные поля игнорируются, в том числе переданный `id`.

### Пример запроса

Замени UUID поставщика в пути на существующий.

```sh
curl -i -X PUT \
  http://localhost:8080/api/v1/suppliers/11111111-1111-4111-8111-111111111111/address \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{
    "country": "Россия",
    "city": "Казань",
    "street": "Ленина"
  }'
```

### Успешный ответ

Статус: `200 OK`. Заголовок ответа: `Content-Type: application/json`.
В JSON возвращается установленный адрес. Поле `id` содержит его UUID;
у поставщика сохранён такой же `address_id`.
UUID ниже приведён для примера.

```json
{
  "id": "33333333-3333-4333-8333-333333333333",
  "country": "Россия",
  "city": "Казань",
  "street": "Ленина"
}
```

Если все три поля совпадают с текущим адресом, возвращается этот адрес с прежним
UUID без создания записи и изменения `address_id`. Сравнение точное, с учётом
регистра и пробелов. Последовательный повтор одинакового PUT сохраняет UUID.

Перед вставкой читается текущий адрес поставщика. Если поставщика нет, возвращается
`404` без вставки адреса. Чтение текущего адреса, создание нового адреса и изменение
ссылки выполняются в одной транзакции. При ошибке изменения отменяются.
Дополнительные блокировки для защиты от параллельных PUT не предусмотрены.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный UUID поставщика, JSON или обязательные поля адреса |
| `404 Not Found` | Поставщик отсутствует; новый адрес не создаётся |
| `500 Internal Server Error` | Ошибка БД |

При отсутствии поставщика ответ будет иметь статус `404`:

```json
{
  "errors": "поставщик не найден"
}
```

При некорректном UUID поставщика в пути ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При ошибке БД сообщение начинается с `ошибка при изменении адреса поставщика:`.
Остальная часть сообщения зависит от этапа операции и причины ошибки PostgreSQL.

## Получение всех поставщиков

```http
GET /api/v1/suppliers
GET /api/v1/suppliers?limit=10&offset=20
```

Возвращает всех поставщиков, отсортированных по `id` по возрастанию.
Наличие товаров и их остаток не влияют на результат. Тело запроса не требуется.
Без параметров возвращает весь список поставщиков.

Пагинация добавлена по согласованию по аналогии со списком товаров.

### Параметры пагинации

Оба параметра необязательны и передаются в строке запроса.
Каждый из них можно использовать отдельно.

| Параметр | Описание | Если отсутствует |
|---|---|---|
| `limit` | Максимальное количество возвращаемых поставщиков; `0` возвращает `[]` | Без ограничения количества |
| `offset` | Количество поставщиков, которые нужно пропустить | `0` |

Значения должны быть целыми числами от `0` до `9223372036854775807`.
Пустые значения, пробелы, дробные и отрицательные числа недопустимы.
Если `offset` не меньше количества поставщиков, возвращается `[]`.

### Примеры запросов

Все поставщики:

```sh
curl -i http://localhost:8080/api/v1/suppliers \
  -H 'Authorization: Bearer <access_token>'
```

Пропустить первых 20 поставщиков и вернуть следующие 10 или меньше:

```sh
curl -i 'http://localhost:8080/api/v1/suppliers?limit=10&offset=20' \
  -H 'Authorization: Bearer <access_token>'
```

Только первые 10 поставщиков:

```sh
curl -i 'http://localhost:8080/api/v1/suppliers?limit=10' \
  -H 'Authorization: Bearer <access_token>'
```

Все поставщики после первых 10:

```sh
curl -i 'http://localhost:8080/api/v1/suppliers?offset=10' \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `200 OK`. Заголовок ответа: `Content-Type: application/json`.
Тело ответа — массив поставщиков с теми же полями, что и при добавлении.

```json
[
  {
    "id": "11111111-1111-4111-8111-111111111111",
    "name": "Бытовая техника",
    "address_id": "22222222-2222-4222-8222-222222222222",
    "phone_number": "+7 (900) 123-45-67"
  }
]
```

Если поставщиков нет или страница пуста, возвращается `[]`.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный `limit` или `offset` |
| `500 Internal Server Error` | Ошибка получения или чтения списка поставщиков из БД |

Например, при `limit=-1` ответ будет иметь статус `400`:

```json
{
  "errors": "параметр limit должен быть целым неотрицательным числом. Пример запроса: /api/v1/suppliers?limit=10&offset=20"
}
```

При ошибке БД текст сообщения зависит от причины ошибки.

## Получение поставщика по ID

```http
GET /api/v1/suppliers/{id}
```

Возвращает поставщика по UUID из пути запроса. Тело запроса не требуется.

### Пример запроса

Замени идентификатор в пути на UUID существующего поставщика.

```sh
curl -i \
  http://localhost:8080/api/v1/suppliers/11111111-1111-4111-8111-111111111111 \
  -H 'Authorization: Bearer <access_token>'
```

### Успешный ответ

Статус: `200 OK`. Заголовок ответа: `Content-Type: application/json`.
Возвращаются те же поля, что и при добавлении поставщика.

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "name": "Бытовая техника",
  "address_id": "22222222-2222-4222-8222-222222222222",
  "phone_number": "+7 (900) 123-45-67"
}
```

После смены адреса поле `address_id` содержит UUID нового адреса.

### Ошибки

Ответ с ошибкой имеет заголовок `Content-Type: application/json`.
Поле `errors` содержит строку с сообщением.

| Статус | Причина |
|---|---|
| `400 Bad Request` | Идентификатор в пути не является корректным UUID |
| `404 Not Found` | Поставщик с указанным UUID отсутствует, в том числе после удаления |
| `500 Internal Server Error` | Ошибка получения или чтения поставщика из БД |

При некорректном UUID ответ будет иметь статус `400`:

```json
{
  "errors": "поле id должно содержать корректный UUID"
}
```

При отсутствии поставщика ответ будет иметь статус `404`:

```json
{
  "errors": "поставщик не найден"
}
```

При ошибке БД сообщение начинается с `ошибка при получении поставщика:`.
Остальная часть сообщения зависит от причины ошибки PostgreSQL.
