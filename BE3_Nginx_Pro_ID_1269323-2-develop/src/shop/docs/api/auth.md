# API регистрации, входа и восстановления пароля

Базовый адрес локального приложения: `http://localhost:8080`.
Магазин передаёт данные в AUTH по gRPC на `localhost:50051`.
Все три метода доступны без токена и заголовка `Authorization`.
Для работы запросов необходимо запустить магазин и AUTH.

Тела запросов и непустых ответов передаются в JSON.
Ответы с JSON имеют заголовок `Content-Type: application/json`.
Ответ с ошибкой содержит строковое поле `errors`.

## Регистрация пользователя

```http
POST /api/v1/register
Content-Type: application/json
```

Обработчик `Signup` вызывает одноимённый метод AUTH и возвращает выданные
AUTH access- и refresh-токены.

### Поля запроса

| Поле | Описание | Формат |
|---|---|---|
| `login` | Логин пользователя | Строка, не пустая и не состоящая только из пробелов |
| `email` | Почта пользователя для восстановления пароля | Строка, не пустая и не состоящая только из пробелов |
| `role` | Роль пользователя | Строка, не пустая и не состоящая только из пробелов |
| `password` | Пароль пользователя | Непустая строка |
| `name` | Имя пользователя | Необязательная строка, без валидации |
| `surname` | Фамилия пользователя | Необязательная строка, без валидации |
| `phonenumber` | Номер телефона пользователя | Необязательная строка, без валидации |

Поля `login`, `email`, `role` и `password` обязательны.
Поля `name`, `surname` и `phonenumber` можно не передавать или оставить пустыми.
Формат email и допустимые значения роли магазин не проверяет.
Магазин передаёт значения без обрезки пробелов
и не хэширует пароль: проверка требований к паролю и хэширование выполняются в AUTH.
Тело должно содержать один JSON-объект без дополнительных значений или мусора.
Неизвестные поля игнорируются.

### Пример запроса

```sh
curl -i -X POST http://localhost:8080/api/v1/register \
  -H 'Content-Type: application/json' \
  -d '{
    "login": "user",
    "email": "user@example.com",
    "role": "user",
    "password": "Password123!",
    "name": "Иван",
    "surname": "Иванов",
    "phonenumber": "+79001234567"
  }'
```

### Успешный ответ

Статус: `201 Created`. Значения токенов ниже приведены условно.

```json
{
  "access_token": "<access JWT от AUTH>",
  "refresh_token": "<refresh JWT от AUTH>"
}
```

### Ошибки

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный JSON, тип поля, отсутствие обязательного значения или ошибка AUTH `InvalidArgument` |
| `409 Conflict` | AUTH вернул `AlreadyExists`: логин уже занят |
| `500 Internal Server Error` | Остальные ошибки вызова AUTH, включая внутреннюю ошибку и недоступность сервиса |

Например, при пустом логине возвращается `400`:

```json
{
  "errors": "поле login обязательно"
}
```

Сообщение AUTH возвращается в поле `errors` вместе с gRPC-кодом.

## Вход пользователя

```http
POST /api/v1/auth
Content-Type: application/json
```

Обработчик `Signin` передаёт логин и пароль в AUTH.
При успешной проверке возвращает выданные AUTH access- и refresh-токены.

### Поля запроса

| Поле | Описание | Формат |
|---|---|---|
| `login` | Логин зарегистрированного пользователя | Строка, не пустая и не состоящая только из пробелов |
| `password` | Пароль пользователя | Непустая строка |

Правила разбора JSON совпадают с регистрацией. Поля `login` и `password` обязательны.
Пароль передаётся без изменений; проверку хэша выполняет AUTH.

### Пример запроса

Используй данные ранее зарегистрированного пользователя.

```sh
curl -i -X POST http://localhost:8080/api/v1/auth \
  -H 'Content-Type: application/json' \
  -d '{
    "login": "user",
    "password": "Password123!"
  }'
```

### Успешный ответ

Статус: `200 OK`. Значения токенов ниже приведены условно.

```json
{
  "access_token": "<access JWT от AUTH>",
  "refresh_token": "<refresh JWT от AUTH>"
}
```

Для запросов к защищённым [API адресов](address.md#аутентификация),
[API клиентов](client.md#аутентификация), [API товаров](product.md#аутентификация)
[API поставщиков](supplier.md#аутентификация) и [API изображений](image.md#аутентификация)
передавай `access_token` в заголовке `Authorization: Bearer <access_token>`.
Магазин проверяет токен в AUTH перед выполнением обработчика.

### Ошибки

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный JSON, тип поля или отсутствие обязательного значения |
| `401 Unauthorized` | AUTH вернул `NotFound` или `Unauthenticated`: пользователь не найден либо пароль неверен |
| `500 Internal Server Error` | Остальные ошибки вызова AUTH, включая ошибку создания токенов и недоступность сервиса |

Например, при неверном пароле возвращается `401`:

```json
{
  "errors": "rpc error: code = Unauthenticated desc = invalid login and/or password"
}
```

Сообщение AUTH возвращается в поле `errors` вместе с gRPC-кодом.
При ошибке соединения текст зависит от причины сбоя.

В текущем серверном `Signin` любая ошибка поиска пользователя преобразуется
в `NotFound`. Поэтому магазин вернёт `401` и при ошибке хранилища,
которую AUTH представил этим кодом.

## Восстановление пароля

```http
POST /api/v1/reset
Content-Type: application/json
```

Обработчик `ResetPassword` передаёт логин в одноимённый метод AUTH.
AUTH создаёт временный пароль, меняет пароль пользователя и вызывает
заглушку отправки письма: временный пароль выводится в консоль AUTH.
Магазин не получает и не возвращает пароль.

### Поля запроса

| Поле | Описание | Формат |
|---|---|---|
| `login` | Логин зарегистрированного пользователя | Строка, не пустая и не состоящая только из пробелов |

Поле обязательно. Значение передаётся без обрезки пробелов.
Правила разбора JSON совпадают с регистрацией и входом.
У пользователя в AUTH должен быть указан email.
Для этого при регистрации через магазин передай поле `email`.

### Пример запроса

Используй логин пользователя, у которого в AUTH заполнен email.

```sh
curl -i -X POST http://localhost:8080/api/v1/reset \
  -H 'Content-Type: application/json' \
  -d '{
    "login": "user"
  }'
```

### Успешный ответ

Статус: `204 No Content`. Тело ответа отсутствует.
Временный пароль можно увидеть в консоли AUTH вместо отправки письма.

### Ошибки

| Статус | Причина |
|---|---|
| `400 Bad Request` | Некорректный JSON, тип поля, пустой логин или ошибка AUTH `InvalidArgument` (у пользователя нет email) |
| `404 Not Found` | AUTH вернул `NotFound` при поиске пользователя |
| `500 Internal Server Error` | Остальные ошибки вызова AUTH, включая создание или сохранение временного пароля, уведомление и недоступность сервиса |

Например, при отсутствии email возвращается `400`:

```json
{
  "errors": "rpc error: code = InvalidArgument desc = email is empty"
}
```

В текущем серверном `ResetPassword` любая ошибка поиска пользователя
преобразуется в `NotFound`. Поэтому ошибка хранилища на этом этапе
также приведёт к HTTP `404`.
